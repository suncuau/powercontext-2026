# 周边去哪儿：高德步行地点推荐

## 目标与运行条件

完成一次“理解需求 → 高德地点搜索 → 高德步行路线查询 → 筛选排序 → 简洁推荐”。所有地点都是从用户给定的同一起点出发的独立备选，不串成多站路线。

使用宿主已配置的高德 MCP 工具；不索取或填写 API Key，不自行配置服务，不安装依赖，不接入记忆或数据库，不导出调用日志。地点与路线必须来自本轮实际成功的高德调用，不能靠记忆、示例、其他地图或搜索网页补造。

## 1. 提取需求

在内部整理以下字段，不必向用户展示分析过程：

- `city`：用户指定城市。
- `origin`：用户提供的起点坐标，按工具要求使用“经度,纬度”，保留原坐标数值；不能改成地铁站中心、城市中心或另一个出口。不要再做设备或 IP 定位。
- `category`：地点类型、品牌或必要关键词；把“喝杯咖啡”归为咖啡馆等，保留“不去某品牌”等排除条件。不要把“安静”“少排队”当作可以凭搜索关键词证明的属性。
- `time_limit`：步行时间硬上限。将分钟换算成秒用于筛选；“不超过/以内”包含边界，“少于/不到”不包含边界。用户没给上限就不添加默认上限。
- `count`：用户要求的数量，默认 3，最终最多 3；用户要求 1 或 2 时遵守更小数量，要求超过 3 时简短说明最多推荐 3 个。
- `preferences`：区分必须满足的条件与“优先、最好”等软偏好，保留用户明确的优先级。预算、营业、无障碍等硬要求缺乏证据时，不能宣称满足。

正常评测输入已有城市和明确坐标，直接查询，不重复追问。仅在坐标缺失、非法，或城市与坐标有明确冲突且无法确认时，简短请求澄清，不猜测位置。未指定地点类型但表示“随便逛逛”时，可搜索公园、咖啡馆等少量不同类型，并说明选择范围。

## 2. 对接高德工具

先查看当前环境提供的工具说明和输入 schema，按能力选择工具。工具名可能带命名空间；下列名称仅用于识别常见对应项，实际名称、字段、类型、单位和可选参数以当前工具定义为准，不调用未提供的工具。

| 能力 | 常见工具名 | 核心输入与用途 |
| --- | --- | --- |
| 周边搜索 | `maps_around_search` | `location=origin`，`keywords=类型或关键词`，可选 `radius`；取得 POI 候选 |
| 步行路线规划 | `maps_direction_walking` | `origin=原始起点`，`destination=该 POI 的 location`；取得步行 paths |
| 关键词搜索（可选） | `maps_text_search` | `keywords` 与 `city`；仅在周边搜索不可用或需补充候选时使用 |
| 地点详情（可选） | `maps_search_detail` | 搜索返回的 POI `id`；仅在需要补全地址、坐标或核实属性时使用 |

周边搜索不支持 `city`、排序、分页、类型等参数时不要强行传入；支持时才使用。关键词城市搜索不能替代步行核验，也不能把全市结果直接称为“附近”。没有可用地点搜索或步行规划能力时，说明缺少相应服务，不能模拟调用成功。

## 3. 搜索并整理候选

1. 以 `origin` 为中心，使用最直接的地点类型关键词查询。可使用工具明确支持的 POI 类型筛选，但不猜测分类代码。区分“咖啡馆”与“咖啡器具店”等非目标类型。
2. 搜索半径只是召回策略：有 T 分钟上限时，首轮可取 `max(1000, 100 × T)` 米；没给时间上限时可取 2000 米。遵守工具允许的半径范围；不支持半径则使用其默认值。该策略不代表步行速度，也不能据此认定可达或排除所有范围外地点。
3. 保留每个候选的 POI ID、原始名称、地址、坐标、类型、城市及已返回的相关属性。按 POI ID 去重；没有 ID 时结合名称、地址和坐标去重，不把同品牌不同分店合并，不混用分店地址和坐标。
4. 先排除明确类型不符、用户明确排除、城市明确不符的候选。没有城市字段不能仅据此判定跨城；需结合搜索上下文与已有地址判断。缺少坐标时可查详情补全，仍缺失则不能查询路线或作为推荐。
5. 优先处理类型明确、基础信息完整且搜索距离较近的候选。搜索返回的距离只能辅助安排核验顺序，不能充当最终步行距离或步行时间。
6. 首批尽量核验 6 个候选（不足时全部核验），让最终最多 3 个结果有比较依据。若合格结果不足或还有明显值得比较的候选，再补查。默认至多核验 12 个不同 POI、进行 3 轮不同的搜索；平台另有限制时优先遵守。
7. 需要补充时，优先处理已返回但未核验的候选，再按工具支持情况分页、换同义关键词或适当扩大半径。扩大搜索范围不能放宽时间、类型或其他硬条件。不足数量允许少推荐，不必为凑数耗尽预算。

## 4. 查询步行路线并校验

对待核验的每个 POI，实际调用步行路线规划，起点始终使用同一个 `origin`，终点使用这个 POI 的真实坐标。不能用驾车、骑行、公交、直线距离测量或自行估算的步速替代步行规划。

读取成功响应中的实际路线字段，保留该 POI 与响应的对应关系：

- 验证响应不是报错，且存在有效步行路径。空 `paths`、错误字符串、缺字段不等于零距离或零耗时。
- 从同一条路径读取总距离和总耗时。常见字段为 `paths[].distance` 和 `paths[].duration`；有的封装使用不同嵌套结构，按其定义读取，例如明确提供的 `cost.duration`。不能误读步骤数量或将路径级与步骤级数据重复累加。
- 距离通常为米、耗时通常为秒，但必须依据工具定义或明确单位确认；将数值字符串解析为数值。单位不明、非有限数、负数或缺失时间/距离的路线不作为有效推荐依据，不自行补算总耗时。
- 如果距离或耗时为零而起终点明显不同，视为异常，复核或跳过；起终点确实重合且工具明确返回有效零值时可以保留。
- 若返回多条有效步行路径：用户明确要求最短距离时选距离最短的一条；其余情况选耗时最短的一条。存在时间等硬上限时先去掉不满足的路径，再按上述规则选择。距离和耗时必须取自最终选中的同一条路径。
- 对每个候选保存内部工作记录：`POI 标识、名称、地址、坐标、所选路线、distance_m、duration_s、约束是否满足、未核实项`。无需输出或保存 JSON 文件。

## 5. 筛选与排序

先执行硬条件筛选，再排序，最后截取所需数量：

1. 推荐必须类型匹配、未被排除、有可关联的真实 POI 和有效步行路线。
2. “T 分钟以内”用原始 `duration_s <= T × 60` 判断；“少于 T 分钟”用 `<`。距离上限也用原始路线距离判断。先过滤再做展示换算，不能将超时结果四舍五入成合格。
3. 明确的其他硬条件须有证据支持。未核实营业状态的商家不能作为“必须现在营业”的合格推荐；若该项只是软偏好，则允许保留并注明未核实。
4. “优先近一点/距离近”按所选路线的步行距离升序，耗时作为并列次序；“尽快到/用时短”按耗时升序，距离作为并列次序。无排序偏好时默认耗时、距离依次升序。多项偏好按用户明确优先级处理，不以未经核实的属性打分。
5. 若用户优先考虑预算、评分等属性，只能使用工具明确返回且口径可比的数据；未知值不当作优值，说明无法充分核实。不要用直线距离排序后声称步行最近。
6. 推荐理由只引用可核实的类型、步行时间、距离及其他已返回事实，例如“咖啡馆类型符合需求，在本次合格候选中步行距离最短”。不宣称全城最近、全网最佳。

## 6. 输出格式

默认中文，开头一句交代地点类型、有效约束和排序方式，然后给出最多 3 行表格；也可用等价短列表：

| 地点 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 高德返回的名称（保留分店名） | 高德返回的地址 | 路线距离，米 | 路线耗时换算为分秒 | 一句有依据的理由 |

- 表格示意项不是实际地点，不将它们填入正式回答。每一行都须能对应本轮高德 POI 和成功步行路线响应。
- 距离优先用米保留返回精度；较大距离可换算为公里并保留足够精度。时间优先展示“X 分 Y 秒”（整分钟可省略秒），并使用“预计”，避免整数分钟掩盖阈值附近差异。
- 地址缺失时优先查详情；无法补全则写“高德未返回地址”，优先选择信息完整的合格候选，不能编造门牌号。名称或地点身份无法确认则不推荐。
- 不必输出坐标、POI ID、原始响应、逐步工具过程或长篇路口指引；若用户特别要求可补充已核实信息。
- 结尾可简述“以上均从同一起点独立步行出发，距离与耗时来自高德步行规划，实际通行以现场为准”。
- 安静程度、排队、座位、营业状态等，仅当与用户需求或推荐理由相关时说明核实情况；没有充分、适用的证据就写“未核实”。营业时间表不自动证明实时营业，不能把店名或营销描述当作验证。

## 7. 空结果、缺信息与服务异常

- **部分合格：** 只列合格结果，说明“本次查询并核验的候选中，仅 N 个满足……”。可简述其余因超时、类型不符、路线无法核实等未列入。不要用不合格备选填满主推荐表。
- **正常查询但无合格结果：** 不输出推荐表，说明“本次查询范围内未找到已核实且满足条件的地点”，给出最相关的调整建议，例如放宽步行时间或更换类型，但不擅自应用该调整。
- **个别路线失败：** 对临时错误重试一次，仍失败则跳过，继续其他候选；有成功结果时照常返回，并简述覆盖不完整。
- **超时、临时网络错误、限流或服务不可用：** 遵守工具明确的等待提示后做一次有限重试，不高频循环。参数错误按 schema 修正后重试一次。鉴权或未配置错误直接说明服务配置不可用，不向用户索取密钥。
- **全部搜索或路线失败：** 明确说“查询失败，暂时无法核实”，不能说成附近不存在地点。可建议稍后重试；不得编造地点或改用估算路线。
- **达到查询预算：** 返回已有合格结果并说明“基于本次已查询并核验的候选”，不能把未查到当成全范围不存在。

## 8. 回答前自检与边界例子

自检：数量不超过用户要求及 3；每行有真实搜索依据和成功步行路线；所有路线同一起点；硬条件全部满足；排序与原始路线数值一致；名称、地址、路线没有跨 POI 混配；未核实信息未被写成事实。

以下仅是规则示例，不能当作真实地点数据使用：

- 上限 15 分钟，路线耗时 900 秒可入选，901 秒不可入选；不能把 901 秒显示为“约 15 分钟”后判合格。
- “优先近一点”：A 的步行路线 600 米/540 秒，B 为 700 米/480 秒，二者均符合时间上限时 A 在前；若用户改为“最快到”，则 B 在前。
- 用户要 3 家，只有 2 家成功核实且合格，就推荐 2 家并说明不足；0 家合格就如实返回空结果，不虚构第三家。
- 搜索距离 200 米但步行路线耗时 1200 秒，在 15 分钟上限下必须排除；不能用 200 米估算出几分钟替代路线结果。
